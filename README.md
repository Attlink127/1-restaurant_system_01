# ระบบร้านอาหาร / สั่งอาหาร (Restaurant Ordering)

ระบบรับออเดอร์ในร้าน สั่งหลายเมนูต่อใบ ผูกลูกค้าและโต๊ะ
มีชุดคอมโบ สมาชิก รีวิว การรับชำระเงิน และใบเสร็จ

## โครงสร้างโปรเจกต์

- `app.py` — หน้าเว็บและ REST API
- `db.py` — เชื่อมต่อ MySQL, CRUD, ออเดอร์, ระดับสมาชิก และรายงาน
- `restaurant_ops.py` — รายละเอียดออเดอร์ เช็กบิล ค้นหาการชำระเงิน ใบเสร็จ และตรวจรีวิว
- `schema.sql` — โครงสร้างฐานข้อมูลทั้งหมดและข้อมูลตัวอย่าง อยู่ในไฟล์เดียว
- `config.py` — ค่าการเชื่อมต่อฐานข้อมูลของเครื่องที่ใช้งาน
- `static/` — JavaScript และ CSS
- `templates/` — หน้า HTML และแบบพิมพ์ใบเสร็จ
- `requirements.txt` — ไลบรารีที่ต้องใช้

## เริ่มใช้งานบนเครื่องที่มีฐานข้อมูลแล้ว

1. ติดตั้งไลบรารี `pip install -r requirements.txt`
2. ตั้งค่า MySQL ใน `config.py` ให้ตรงกับเครื่อง
3. รัน `python app.py`
4. เปิด http://127.0.0.1:5000

ฐานข้อมูลบนเครื่องปัจจุบันที่มีตารางครบแล้วใช้งานต่อได้ทันที
ไม่ต้องรัน schema.sql ซ้ำบนฐานข้อมูลที่มีประวัติอยู่

## สร้างฐานข้อมูลใหม่สำหรับเครื่องใหม่

1. สร้างฐานข้อมูล MySQL ชื่อ `project69` โดยใช้ utf8mb4
2. เปิดและรัน `schema.sql` บนฐานข้อมูลใหม่นั้นหนึ่งครั้ง
3. ตั้งค่า `DB_NAME` ใน `config.py` ให้ตรงกับชื่อฐานข้อมูล

schema.sql เป็นไฟล์สำหรับสร้างตารางและข้อมูลตัวอย่างใหม่
ถ้าต้องใช้ชื่อฐานข้อมูลอื่น ให้แก้คำสั่ง USE ใน schema.sql ให้ตรงกัน

## ตารางและความสัมพันธ์

- `customer` — ลูกค้าและระดับสมาชิก
- `menu_item` — เมนู ราคา และสถานะการขาย
- `dining_table` — เลขโต๊ะ จำนวนที่นั่ง และโซน
- `food_order` — หัวออเดอร์ เชื่อมลูกค้าและโต๊ะด้วย FK
- `order_item` — รายการอาหารในออเดอร์ เชื่อมออเดอร์กับเมนูแบบ M:N
- `combo` — ส่วนประกอบของชุดเมนู มี combo_id เป็น PK และ UNIQUE(item_id, sub_item_id)
- `review` — คะแนนและความคิดเห็นของลูกค้า
- `payment` — การชำระเงิน เก็บประวัติหลายบิลต่อออเดอร์ โดยมีบิล PAID ได้ครั้งเดียวด้วย UNIQUE(active_order_id)

## กติกาการใช้งาน

- เมนูไม่ลบแถวจริง ปุ่มเลิกขายเปลี่ยน is_discontinued=1 และ is_available=0
  หากหมดชั่วคราวใช้ is_available=0, is_discontinued=0 และเปิดขายใหม่ได้ในฟอร์มแก้ไข
- เก็บ qty และ unit_price ใน order_item เพื่อรักษาราคาตอนสั่ง
  ยอดอาหารรวมคำนวณ SUM(qty * unit_price) และเซิร์ฟเวอร์เป็นผู้กำหนดราคา
- ออเดอร์ผูกโต๊ะ ออเดอร์ไม่ยกเลิกและยังไม่จ่ายจะทำให้เปิดออเดอร์ใหม่บนโต๊ะเดิมไม่ได้
- สถานะอาหาร: PENDING, IN_PROGRESS, READY, COMPLETED, CANCELLED
  COMPLETED หมายถึงเสิร์ฟครบ ยังแยกจากสถานะชำระเงิน
- ลูกค้าใหม่เริ่ม Regular ยอดอาหารสะสมจาก COMPLETED ครบ 3,000 บาทเป็น Gold
  ครบ 10,000 บาทเป็น VIP เลื่อนขึ้นเท่านั้น ไม่ลดสิทธิ์ที่เคยได้รับ
- เช็กบิลจากรายละเอียดออเดอร์ที่เสิร์ฟครบแล้ว ส่วนลด ณ ตอนจ่ายคือ Regular 0%, Gold 5%, VIP 10%
- รับเงินสดหรือบันทึกโอนโดยพนักงานยืนยัน ไม่เชื่อมธนาคารอัตโนมัติ
  ใช้ Decimal คิดเงินและปัดส่วนลดสองตำแหน่ง ตรวจยอดก่อนบันทึก
- บิลที่จ่ายแล้วแก้ไขหรือลบออเดอร์ไม่ได้ และรับชำระซ้ำไม่ได้
- ใบเสร็จเก็บสำเนาชื่อเมนู ลูกค้า ราคา และส่วนลดตอนจ่าย เพื่อไม่เปลี่ยนตามข้อมูลปัจจุบัน
  ยอดรวมและส่วนลดใน payment เป็นหลักฐาน ณ เวลารับเงิน ส่วนยอดออเดอร์ทั่วไปคำนวณจากรายการ
- แท็บการชำระเงินค้นบิลตามเลขออเดอร์ ชื่อลูกค้าในใบเสร็จ วันที่ และวิธีจ่าย พร้อมพิมพ์ย้อนหลัง
- รีวิวต้องอ้างออเดอร์ COMPLETED ของลูกค้าที่เลือก ตรวจทั้งหน้าเว็บและเซิร์ฟเวอร์
- ชุดคอมโบสั่งผ่านเมนูชุดหลัก คิดราคาจาก menu_item.price ของชุด ไม่บวกราคาองค์ประกอบซ้ำ

## รายงาน

1. เมนูขายดี 5 อันดับ — JOIN + GROUP BY + SUM(qty) + LIMIT
2. มูลค่าอาหารต่อวันก่อนส่วนลด — GROUP BY DATE + SUM(qty * unit_price)
3. ออเดอร์เกิน 500 บาท — GROUP BY order + HAVING SUM(...) > 500
4. ยอดตามหมวดหมู่ ลูกค้ายอดสูง และรีวิว
5. เงินรับจริงหลังส่วนลดต่อวัน — รวม payment ตามวันที่ชำระ

รายงานอาหารนับเฉพาะ COMPLETED รายงานรับเงินจริงนับเฉพาะ payment ที่บันทึกสำเร็จ
ออเดอร์เก่าที่ไม่มี payment ถือว่ายังไม่มีข้อมูลการรับเงิน ไม่สร้างประวัติการจ่ายแทนให้เอง

## การทำงานของโค้ด

- ใช้ %s พร้อม params แยกจาก SQL ป้องกัน SQL injection
- บันทึกออเดอร์และการรับเงินภายใต้ transaction พร้อม rollback เมื่อผิดพลาด
- ล็อกแถวออเดอร์/โต๊ะ/ลูกค้าที่เกี่ยวข้องเพื่อป้องกันการเปลี่ยนข้อมูลระหว่างดำเนินการ
- เพิ่มรายงานโดยเขียนฟังก์ชันใน db.py แล้วเพิ่มรายการใน REPORTS


## การยกเลิกบิลที่บันทึกผิด

- ใช้เฉพาะรายการยืนยันรับเงินผิด โดยพนักงานต้องกรอกเหตุผลและยืนยันว่าบิลนี้ยังไม่ได้รับเงินจริง
- ไม่ใช่การคืนเงิน และไม่ลบแถว payment: คงยอดเดิม snapshot เหตุผลและเวลายกเลิกไว้เสมอ
- payment.status เป็น PAID หรือ CANCELLED; รายงานรับเงินจริงรวมเฉพาะ PAID
- UNIQUE(active_order_id) อนุญาตบิล PAID หนึ่งใบต่อออเดอร์ และเก็บบิลที่ยกเลิกได้หลายใบ
- หลังยกเลิกสามารถแก้ออเดอร์และรับชำระใหม่ เลขใบเสร็จใหม่ไม่ใช้เลขเก่า
  ออเดอร์ที่มีประวัติ payment แม้ยกเลิกแล้วก็ลบไม่ได้ เพื่อรักษาหลักฐาน
- การยกเลิกบิลออเดอร์ที่เสิร์ฟจบแล้วไม่ทำให้กลับไปจองโต๊ะเก่าที่อาจมีลูกค้ารายใหม่
- ใช้ transaction และล็อก food_order ก่อน payment เหมือนตอนรับเงิน ป้องกันกดซ้ำ/ทำงานพร้อมกัน
- ยอดอาหารก่อนส่วนลดและเกณฑ์สมาชิกยังอิง COMPLETED ตามกติกาเดิม ไม่ใช่ยอดรับเงินจริง


### ลบเฉพาะใบเสร็จจากรายการ
- ปุ่มลบในหน้าการชำระเงินตั้ง payment.receipt_deleted_at แล้วกรองใบเสร็จออกจากรายการ
- ไม่เปลี่ยนสถานะ PAID/CANCELLED ไม่แก้ยอดรับเงินจริง และไม่เปิดให้ออเดอร์ที่ชำระแล้วรับเงินซ้ำ
- ไม่ลบแถว payment หรือ snapshot เพื่อเก็บข้อมูลรับเงินสำหรับรายงาน
- อยู่หน้าใบเสร็จหลังลบ ไม่มีฟอร์มเหตุผล กู้ไฟล์เก่าไม่ทำให้ข้อมูลที่ซ่อนไว้กลับมา
- บิลที่เคยยกเลิกก่อนหน้านี้ยังเป็น CANCELLED ตามเดิม ไม่คืนสถานะ PAID อัตโนมัติ


### กำหนดระดับสมาชิกในฟอร์มลูกค้า
- เพิ่มและแก้ไขลูกค้าเลือกระดับ Regular / Gold / VIP ได้ โดยลูกค้าใหม่เริ่มต้นที่ Regular
- API ตรวจค่าระดับให้ตรงกับ ENUM และยังตรวจเบอร์โทร 10 หลัก
- การแก้ข้อมูลโดยไม่ส่ง member_tier จะคงระดับเดิมไว้
- กำหนดระดับเองขึ้นหรือลงได้ แต่การเลื่อนอัตโนมัติตามยอดสะสมยังทำงานเมื่อบันทึกออเดอร์ครั้งถัดไป
- ใบเสร็จเดิมใช้ระดับและส่วนลดจาก snapshot ตอนชำระ ไม่คิดเงินย้อนหลังใหม่
